## Raspberry Pi 3B+ の使い道

現場で使われ最近退役した **Raspberry Pi 3B+** と、引き出しに転がっていた **格安 USB HDMI キャプチャドングル**（MacroSilicon 系のよくあるやつ）で、追加投資ゼロの KVM-over-IP、つまり PiKVM を組めないか試してみた記録。

結論だけ先に言うと、**HDMIの映像は出せた**。ただし公式ドキュメントの本流から外れた構成で、ビデオキャプチャの段階に至らず。

長くなるので前後編に分ける。

- **前編（この記事）**：ビデオキャプチャで映像が出るまで。
- **後編**：HID（キーボード/マウス）エミュレーション編。こちらは **電源＋キーボードエミュレーション分岐ケーブルの到着待ち**なので、モノが届いてから。

---

## そもそも 3B+ × USB ドングルは「公式の本流」ではない、という前提

ハマった原因の話をする前に、地図を確認しておきたい。ここを知らずにエラーメッセージだけ追うと、延々と設定ファイルをいじる羽目になる（なった）。

PiKVM の公式イメージ／パッケージ体系は、力点が明確に **RPi4 と商用デバイス（V3 HAT / V4）** に寄っている。

- 公式の DIY V2 イメージは実質 `rpi4`（と `zero2w`）向け。`v2-hdmi`（HDMI-CSI ブリッジ）と `v2-hdmiusb`（USB ドングル）が用意されている。
- 現行の公式 `kvmd` パッケージ（PKGBUILD）がビルドする V2 系プラットフォームは **`v2-hdmiusb:rpi4` のみ**。つまり `v2-hdmiusb-rpi3` という組み合わせは、少なくとも現行の公式ビルド対象には**存在しない**。
- RPi2 / 3B+ の DIY は世代的に **V1**（`v1-hdmiusb-rpi3`）相当。公式のビルド手引きでも「RPi2 or 3B+ + HDMI-USB ドングル + **Pico HID**」という書き方で、3B+ は HID を出すのに外付けマイコン前提、という扱い。
- 3B+ 向けの USB ドングルイメージそのものも、コミュニティ（例：`srepac/kvmd-armbian`）が参照する `kvmd-platform-v0-hdmiusb-rpi3` のような**レガシー／サードパーティ配布**の色が濃い。

要するに、**「3B+ に USB ドングル」は公式が力を入れて整備しているレーンではない**。ドキュメント本文は RPi4 と CSI ブリッジ（V3/V4）前提で書かれていて、DIY 側はその派生の注記として散らばっている。この構造のせいで、**「USB ドングル用イメージを入れたつもりでも、実際に効くビデオ設定は CSI/GPIO 前提のまま」** という土台のズレが起こりうる。　デグレても拾われない派生物の悲しさ。

おまけに、USB キャプチャ経路は PiKVM 公式自身が格下として説明している。要約すると、重い MJPEG のみ・解像度の自動検出なし・CSI 比でレイテンシ大、そしてドングルによっては BIOS が映らなかったり一定時間で止まったりする個体差あり、とのこと。つまり **「格安 USB ドングル + 3B+」は、公式が想定する快適ラインから二重に外れている**。「なぜドキュメント通りに映らないのか」の答えは、だいたいこれで説明がつく。

## ビデオキャプチャで刺さった話。

以下、実機で起きたことを時系列で。

### カーネルはちゃんとドングルを見ている

まず OS 層を疑う。`v4l2-ctl` を叩くと、

```console
[root@pikvm ~]# v4l2-ctl --list-devices
USB Video: USB Video (usb-3f980000.usb-1.4):
        /dev/video0
        /dev/video1
        /dev/media0
```

`/dev/video0` が実ストリーム、`/dev/video1` はメタデータ用にペアで生成される、V4L2 のよくある挙動。**カーネルは問題なくドングルを掴んでいる**。狙うべきは `/dev/video0`。ここまでは順調に見えた。

### なのに PiKVM 側は映像を出さない

`v4l2-ctl` では見えているのに、Web UI には映像が出ない。いじっているうちに最終的には `NO CAPTURE DEVICE` まで出た。ログはこう。

```
kvmd.apps.kvmd.streamer.runner  INFO  --- => -- ERROR [....  stream]
-- No access to capture device: No such file or directory
```

OS からは見えているデバイスに対して「そんなファイルは無い」??? 

実体は、**ストリーマーがドングルの `/dev/video0` ではなく、CSI 前提のデバイスパス（`/dev/kvmd-video`）側を掴もうとしていた**こと。つまり、効いているプラットフォーム構成が USB ドングルに合っていなかった。開発者が、すでに打ち捨てた過去のシステムでデグレードすることを想定しないことはよくあることだが、ダウンロード可能なイメージとして名前を付けてあったので、かなり大きめの罠だ。

### あれこれ触っているうちにカラーバーが出た

プラットフォーム構成を USB ドングル側に寄せて `kvmd` を再起動していたら、あるとき **カラーバー（テストパターン）** が出た。

PiKVM のカラーバーは「**ustreamer は正常に動いていて、キャプチャデバイスは掴めているが、入力に HDMI 信号が来ていない（No Signal）**」の意味。地味だが、これは大きな前進で、この時点で**ソフト側は片付いた**ことになる。残りは物理信号の問題だけ。

### 最後は信号側を落ち着かせて実映像

ターゲット PC が休眠していたので、HDMI ケーブルを挿し直してホットプラグを再検出させる——で、無事に実画面が表示された。

なお格安ドングルは 1080p60 をそのまま食わせると信号を落としてカラーバーに戻るそうである（未検証）　なので**まず 720p か 1080p30 で当たりを取る**のが定石。映ってから徐々に上げて限界を探っていこうと思う。

## 結局、最初に打つべきだった 3 つ

回り道の反省として、最初にこれをやっていれば早かった、という順。

**1. いま効いているプラットフォームを確定させる**

```console
[root@pikvm ~]# pacman -Q | grep kvmd-platform
```

表示される `kvmd-platform-*` が、実際に効いているハード構成そのもの。USB ドングルのつもりなら `*-hdmiusb-*` のはず。`*-hdmi-*`（CSI）だったらイメージ選択の時点で不一致で、`override.yaml` を何行足しても徒労になる。

**2. カーネル側の認識と突き合わせる**

```console
[root@pikvm ~]# v4l2-ctl --list-devices
```

「カーネルは `video0` で見えているのに、プラットフォームは別パスを見に行っている」というズレが可視化できれば、原因は確定。

**3. 自分の差分だけを見る**

```console
[root@pikvm ~]# kvmd -M    # ← 大文字。ユーザ override だけ
```

`kvmd -m`（小文字）は**マージ後の全パラメータ**を吐くので、GPIO サブシステム等の正常なデフォルト（`/dev/kvmd-gpio` など）まで大量に出てきて、慣れないと「USB ドングルなのに GPIO を読んでる、おかしい」と誤読しがち。`-M` なら自分が足した差分だけが見える（override がコメントのみなら、ここは空になる）。

---

## 誤読しやすかったポイント

はまりどころを軽くメモしておく。

- **`kvmd -m` の GPIO エントリは異常ではない。** `/dev/kvmd-gpio` は ATX 電源制御やユーザボタン用の GPIO サブシステムのもので、どのプラットフォームでも出る。USB ドングル関係なく正常。
- **`NO CAPTURE DEVICE` の記事化事例が少ないため対応に苦慮する。** `No access to capture device` は、掴みに行くデバイスパスの不一致であることが多い。パス（`video0` vs `kvmd-video`）とプラットフォームを先に疑う。
- **基盤ファイルは `/usr/lib/kvmd/main.yaml`（編集厳禁）。** 上書きは `/etc/kvmd/override.yaml` に。`/etc/kvmd/platforms` みたいなパスは存在しない。
- **EDID 制御（`Change EDID` / `Reset HDMI`）は CSI ブリッジ専用。** TC358743 を積んだ V3/V4 等でのみ有効で、USB ドングル構成にはそのボタン自体が無い。EDID はドングルの物理仕様任せ。

---

## 前編で残った宿題（その他の問題）

- **DisplayPort → HDMI 変換で映るか未検証。** ターゲットが DP 出力の場合、変換は必ず **アクティブ型**を。パッシブ型（DP++ 依存）は格安キャプチャ相手だと No Signal に戻りやすい。BIOS まで確実に映したいなら、可能なら変換を挟まず直 HDMI が堅い——というのは定説だが、手元での実測はこれからである。なお、この前段にリアルデバイスのKVMをいれるので「物理スイッチ」をどう調理するか（まあ、キー組み合わせ切り替えは装備されていると思うが、コンソールではボタン切り替えに頼っていたのでテストしていない）という話が残っている。　現場で EDID対応の DPドライバをすべてのサーバOSで対応したはずなので、KVM側の切り替えは有効になっていて、あとはHDMIキャプチャデバイスがそれに耐えられるかである。

## 後編予告：HID（キーボード/マウス）エミュレーション編

映像は出たが、KVM としてはまだ「見えるだけ」で、操作ができない。次はキーボード/マウスのエミュレーションに挑む。

ここで 3B+ ならではの壁がある。native な USB OTG による HID エミュレーションは Pi4 / Pi Zero 系のようには素直に使えず、公式も 3B+ は V1 相当＝**外付け HID（Pico HID など）前提**という扱い。加えて、初心者が 3B+ をそのまま買った状態だと **GPIO 経由の 5V 給電を前提にできない**ため、電源とデータの取り回しがそのままでは噛み合わない。

そこで **電源＋キーボードエミュレーション分岐ケーブル**を手配した。これが届いてから、HID をどう通すか、給電をどう分けるか、を後編でやる予定。
